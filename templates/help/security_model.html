Security Model

Trust Boundaries

sshadmin's security rests on three independently-protected secrets:

  1. The Host CA private key — signs host certificates. If compromised, an attacker could impersonate any enrolled host to clients that trust the CA. Stored on the sshadmin server only.
  2. The User CA private key(s) — sign user certificates. If compromised, an attacker could forge certs granting access to any machine that trusts the CA. In multi-group mode, each group has its own CA key — a compromise affects only that group's machines.
  3. Each host's private SSH key — proves the host's identity. Cannot be extracted from the machine without root access. Host certs are bound to this key.
CA key compromise is critical. Protect the sshadmin server with the same care as your most sensitive machine. Use full-disk encryption, restrict network access, and monitor logins.
What sshadmin Enforces
  • Host authentication — clients verify the host cert against the CA; no more "accept unknown fingerprint?" prompts. A rogue machine cannot impersonate an enrolled one.
  • User authentication — servers verify the user cert against the (group) CA; only cert holders can log in to accounts listed in the cert's principals.
  • Principal restrictions — root is never a valid principal. Users can only be signed for unix accounts explicitly authorised by the host owner.
  • Cert expiry — expired certs are rejected with no server-side action required. Short-lived certs are the primary revocation mechanism.
  • Group isolation (multi-group mode) — a cert signed by Group A's CA is cryptographically rejected by machines that only trust Group B's CA. This is enforced by OpenSSH, not by policy rules that could be misconfigured.
What sshadmin Does NOT Protect Against
  • Compromise of the sshadmin server itself — the CA keys are on this machine. Treat it as a high-value target.
  • A user copying their private key to another machine — the cert follows whoever holds the private key. Passphrase-protect user keys to reduce risk.
  • Root on an enrolled machine — a user who gains root can read /etc/ssh/sshd_config, modify TrustedUserCAKeys, or add entries to /root/.ssh/authorized_keys. This is a property of SSH itself, not of sshadmin.
  • The "default" group in simple mode — everyone is in it. If multi-group isolation is needed, enable multi-group mode and assign machines to appropriate groups.
User Cert Issuance — Who Controls What

A key design goal is that users cannot obtain certificates granting access to accounts the machine owner did not authorise:

  • Simple mode: The unix account name in the cert matches the username provided during enrollment. Users do not choose their own principals.
  • Multi-group mode: Group owners set the allowed unix accounts per user at approval time (the unix principals field). Users can request what they need, but cannot override the group owner's decision.
  • Root is blocked server-side — the cert issuance code refuses to sign a cert with root as a principal regardless of what is requested.

Machine owners control which CA groups their machine trusts. This means they decide which sets of users can reach their machine, without needing to manage individual key entries.

Host Principal Mode (Strict vs. Wildcard)

Host certificates can be issued in two modes, configurable in Admin Settings:

Wildcard (default)

No -n flag — the cert is valid for any hostname. Security relies entirely on the CA key and the host's private key remaining protected. Clients accept the host as long as the cert is CA-signed and unexpired.

Strict mode

The cert lists all registered hostnames and IP aliases as principals. A client connecting via a name not in the list sees "Certificate invalid: name is not a listed principal." Use sshadmin alias to register additional names.

Note: StrictHostKeyChecking yes is written into the client's ~/.ssh/config by the enrollment script, so cert failures hard-fail rather than falling back to a raw key prompt.
