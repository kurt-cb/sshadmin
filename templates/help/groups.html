CA Groups

The Problem Groups Solve

In the default (simple) mode, all machines trust the same User CA. This means a valid user certificate works on every enrolled machine. That is convenient for small environments where everyone should have access to everything, but becomes a problem when:

  • Accounting staff should not reach production engineering hosts.
  • Contractors need access to specific machines but not others.
  • You want to scope an access breach to a subset of machines.

CA Groups solve this by giving each zone its own CA key. A cert signed by the Accounting CA is cryptographically rejected by a machine that only trusts the Engineering CA — no policy rule, no runtime check, just math.

How Groups Work

There are two independent membership relationships:

Machine → Group

The machine owner requests to join a group. The group owner approves. The machine's TrustedUserCAKeys is updated to include the group's CA public key.

A machine can be in multiple groups, trusting multiple CAs simultaneously. Users from any of those groups can then connect.

User → Group

The user requests group access, specifying which unix accounts they need. The group owner approves and may adjust the allowed accounts. A cert signed by the group CA is then issued to the user.

Group membership grants access to all machines in the group, not just one specific machine.

The machine owner controls which groups their machine trusts (which users can reach it). The group owner controls which users are in the group (who gets a cert). These two decisions are independent — no single person has unilateral control over both.
The foo1 / foo2 Example

Alice is in the Accounting group. Bob is in the HR group.

  • foo1 is in Accounting + HR — trusts both CAs. Both Alice and Bob can log in.
  • foo2 is in HR only — trusts only the HR CA. Bob can log in; Alice's Accounting cert is rejected.
  • foo3 is in Accounting only — Alice can log in; Bob cannot.

No per-machine user lists to maintain. The machine owner's only decision: which groups to join. The group owner's only decision: which users belong.

The Default Group

The default group always exists and uses the main site CA key. In simple mode (multi-group disabled) all users and hosts are in it automatically — behaviour is identical to pre-group operation.

When you enable multi-group mode, the default group remains for hosts and users that don't need isolation. New groups are opt-in; nothing breaks.

Getting a Certificate (Multi-Group Mode)
  1. Register your sshadmin account and upload your public key.
  2. Request access to the group that covers the machines you need (from the Groups page).
  3. The group owner approves your request and sets your allowed unix accounts.
  4. Run sshadmin get-cert on your machine — it SSHes to the sshadmin server, checks your group membership, and downloads a cert signed by the group CA.
  5. ssh alice@foo1 — works immediately. No per-machine setup needed on your end.

Steps 1–3 happen once (or when you need a new group). Step 4 repeats whenever your cert expires (automated with a short-lived cert wrapper or cron job).

When to Use Multiple Groups
  • Departments: Accounting, HR, Engineering each get a group. Staff are in the group(s) they need.
  • Environments: Dev, Staging, Prod groups. Developers are in Dev; ops in all three.
  • Contractors: A narrow group with only the specific machines the contractor needs.
  • Break-glass: An "admin" group with very few members and strict monitoring.

If everyone should reach everything, stay in simple mode. Add groups when you need cryptographic isolation, not just policy enforcement.
